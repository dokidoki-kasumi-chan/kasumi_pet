AI 实习面试模拟 30 题
（AI 开发实习生 + AI 产品实习生·智能体方向）

===========================================================
一、AI 智能体基础（8 题）
===========================================================

Q1: 什么是 AI Agent？它和传统 Chatbot 有什么区别？
A: Chatbot 是"一问一答"，Agent 是"感知-决策-执行-记忆"闭环。
核心区别：Agent 能主动感知环境、调用工具、记住上下文、自主规划步骤。
例子：Chatbot = "今天天气怎么样？"→ 回答。Agent = 检测到你打开了 IDE → 自主
弹出"开始学习啦？要我开番茄钟吗？"→ 调用计时器工具 → 25 分钟后提醒休息。

Q2: Agent 的核心组件有哪些？
A: 四个核心组件：
- 感知(Perception)：获取环境信息（窗口检测、剪贴板读取、时间）
- 规划(Planning)：根据目标分解任务步骤（先做什么、再做什么）
- 执行(Action)：调用工具完成任务（API 调用、切换立绘、弹出气泡）
- 记忆(Memory)：短期（对话历史）+ 长期（好感度持久化、用户偏好）

Q3: 什么是 Function Calling / Tool Use？
A: 让 LLM 在回复过程中主动调用外部函数。LLM 不直接执行，而是输出一个结构化的
"我想调用这个函数"的请求，由程序执行后把结果传回 LLM 继续生成。
例子：用户问"帮我查一下今天天气"→ LLM 输出 `{function: "get_weather", args:
{city: "广州"}}` → 程序调用天气 API → 结果塞回对话 → LLM 生成带温度的回复。
关键：LLM 决定"什么时候调用"和"传什么参数"，但执行在程序侧。

Q4: 多 Agent 协作有哪些常见模式？
A: 三种主流模式：
- 顺序流水线：Agent A 输出 → Agent B 处理 → Agent C 汇总
- 辩论/评审：多个 Agent 独立给出方案，再投票或融合
- 层级调度：一个"主控 Agent"分配任务给子 Agent，汇总结果
面试补充：实际产品中多 Agent 的难点不在于"怎么调用"，而在于上下文传递和错误
传播——一个 Agent 出错会导致整条链路崩。

Q5: 上下文管理怎么做？对话历史太长怎么办？
A: 三大策略：
- 滑动窗口：只保留最近 N 条（如 50 条），旧的丢弃
- 摘要压缩：用另一个 LLM 把旧对话压缩成一段摘要，替代原始历史
- 向量检索：把历史存向量库，只检索与当前问题相关的片段注入 prompt
实际项目中选择哪个取决于延迟和成本的平衡——滑动窗口最简单，摘要压缩适合需要
长期记忆的场景，向量检索适合海量历史。

Q6: Token 成本怎么控制？
A: 四个维度：
- 输入侧：限制用户输入长度，前端硬拦截
- 上下文侧：控制历史条数和 system prompt 长度
- 模型侧：非关键任务用小模型（如分类用纯算法，不调 LLM）
- 架构侧：缓存重复的 system prompt（Anthropic 的 prompt caching 可省 90%）
面试补充：能估算单次对话成本 = (input tokens × 单价) + (output tokens × 单价)。

Q7: 流式响应（Streaming）和非流式有什么区别？
A: 非流式：LLM 生成完整回复后一次性返回，用户要等全部生成完才能看到。
流式(SSE)：LLM 逐 token 推送，用户看到文字一个个出现，体验更"实时"。
选哪个取决于场景：客服/聊天需要流式（用户不想等），批量分析可以非流式。
流式的代价是实现复杂度高——需要处理断连重连、部分内容渲染、中途取消等问题。

Q8: 怎么评估一个 LLM 适不适合你的产品？
A: 五个维度：
- 能力：能否完成核心任务（角色扮演、代码分析、翻译）
- 延迟：回复速度是否在用户可接受范围（<5s 开始输出）
- 成本：单次对话费用（DeepSeek 约 GPT-4 的 1/50）
- 稳定性：API 可用性、模型名和接口是否频繁变更
- 合规：数据存储位置、隐私政策
实际做法：先用最便宜的模型跑通流程，再按需升级。不要一上来就选最贵的。

===========================================================
二、Prompt 工程（5 题）
===========================================================

Q9: 什么是 System Prompt？怎么写好它？
A: System Prompt 是给 LLM 的最高优先级指令，定义角色、行为边界、输出格式。
写好 System Prompt 的三要素：
- 角色定义：你是谁（"你是户山香澄，Poppin'Party 主唱"）
- 行为边界：能做什么/不能做什么（"你不会编程，只会聊天和鼓励"）
- 输出格式：怎么回答（"保持口语化，2-3 句话，不要长篇大论"）
常见错误：写太多矛盾指令、没说"不能做什么"、忘记格式要求。

Q10: 怎么让 LLM 稳定扮演一个角色？
A: 三层控制：
1. System Prompt 写死人格和行为准则（"你永远积极开朗"）
2. 提供台词样本（Few-shot）：给 5-10 句角色原话，让 LLM 模仿语气
3. 运行时参数注入：好感度、时间、场景等变量动态插入 prompt
但 System Prompt 不是万能的——LLM 可能在长对话中"忘记"前面的指令。
所以还需要前端兜底：超长消息拦截、敏感内容过滤、格式校验。

Q11: Few-shot 和 Zero-shot 的区别？
A: Zero-shot：不给示例，直接问（"翻译这段话"）。适合简单任务。
Few-shot：给 2-5 个示例，再问（"示例1→答案1，示例2→答案2...新问题→?"）。
适合需要特定格式或风格的复杂任务。
mibo 的 RAG 台词就是 Few-shot 的变体——把角色原话作为"示例"让 LLM 模仿。

Q12: Prompt 长度和效果的关系？越长越好吗？
A: 不是。太长有三个问题：
1. 成本：input token 要计费的
2. 注意力稀释：LLM 对 prompt 中间段的信息关注度会下降（Lost in the Middle）
3. 延迟：更长的 prompt = 更长的处理时间
原则：能精简就精简，能分层的就分层（核心指令放前面，参考资料放后面）。

Q13: 你怎么调试一个"不听话"的 Prompt？
A: 四步调试法：
1. 简化：把 prompt 缩减到最核心的一句话，看问题是否还存在
2. 补边界：加"你不应该做 X"的负向指令
3. 换措辞：把模糊词换成具体词（"友好一点"→"用 2-3 句话，以'嗨~'开头"）
4. 加示例：给 1-2 个正确答案的 Few-shot
如果以上都无效，可能是模型本身能力不够，需要换模型。

三、AI 产品思维（6 题）
===========================================================

Q14: AI 产品的"魔法时刻"是什么？
A: 用户第一次感受到"这东西不是传统软件"的瞬间。
mibo 的魔法时刻：复制了一段报错代码 → 桌宠自动弹出"报错了吗？要我帮忙看看吗？
"——用户什么都没做，Agent 主动感知并响应了。
面试追问：你的产品有魔法时刻吗？如果没有，用户 30 秒内就会离开。

Q15: AI 产品的留存为什么比传统 App 低？
A: 两个核心原因：
1. 新鲜感衰减快：第一周觉得"好神奇"，第二周就习惯了
2. 期望落差：AI 不是万能的——回答质量不稳定会让用户失望
解法：不要卖"AI 万能"，卖"特定场景好用"。mibo 的定位是"学习伴侣"而非
"万能助手"——用户知道它能做什么，不会对它有不切实际的期待。

Q16: 用户说"AI 回答质量不稳定"，你怎么办？
A: 先拆问题：是偶尔不稳定还是一直不稳定？
- 偶尔：可能是 prompt 太长导致注意力稀释，或模型本身波动
- 一直：可能是 prompt 设计问题，或模型能力不够
然后量化：定义什么叫"好"（准确性、相关性、格式正确率），抽样 100 条评估。
最后迭代：改 prompt → 重新评估 → 对比改进幅度。

Q17: 怎么平衡 AI 的"创造力"和"可控性"？
A: 一个光谱：
创造力端：允许 LLM 自由发挥（适合创意写作、闲聊）
可控性端：严格约束输出（适合客服、数据处理）
mibo 的做法：角色人格给创造力空间（"说话方式像香澄"），但状态切换和交互逻辑
用硬编码规则控制（"凌晨必须睡觉"）。AI 管"怎么说"，规则管"做什么"。

Q18: 大模型幻觉（Hallucination）怎么处理？
A: 幻觉是 LLM 的固有缺陷，无法 100% 消除，只能降低影响：
- 事实型场景：加 RAG，让 LLM 基于检索到的文档回答，而非凭记忆
- 角色扮演场景：约束在角色世界观内（"香澄不知道计算机知识"写进 prompt）
- 前端兜底：检测到不确定的回答，加"仅供参考"标记
关键认知：不是所有场景都要消除幻觉——闲聊时编一个笑话 OK，医疗建议绝对不行。

Q19: 你认为 AI 产品经理和传统 PM 最大的区别是什么？
A: 三个新增能力：
1. Prompt 思维：能写能调 prompt，理解 LLM 的行为模式
2. 不确定性管理：传统 PM 预期"输入 A → 输出 B"，AI 产品是"输入 A → 大概率
   输出 B，偶尔 C，极少数情况下 Z"
3. 技术边界感：知道 LLM 能做什么不能做什么，不画"让 AI 自动完美完成 X"的饼
传统 PM 的看家本领（用户洞察、需求分析、数据驱动）依然适用。

四、AI 协作开发 & 工程化（6 题）
===========================================================

Q20: Claude Code / Cursor 这类 AI 编程工具改变了什么？
A: 改变了"写代码"的经济模型：
- 以前：写一个功能 = 2 小时手写代码
- 现在：描述需求 = 2 分钟 → AI 生成 → 审查 10 分钟 → 修改 20 分钟
省的不是"打字时间"，是"查文档、查 API、处理样板代码"的时间。
但审查和系统设计的时间反而增加了——AI 写的代码更容易有隐蔽 bug。

Q21: 你怎么确保 AI 生成的代码质量？
A: 三个原则：
1. 上下文要给足：CLAUDE.md + memory + references 让 AI 了解全貌
2. 小步迭代：一次只改一个功能，不要"全部重写"
3. 人审 AI 改：AI 负责生成 diff，人负责判断"这个改动对系统的影响"
最难的不是让 AI 写代码，而是让 AI 在正确的上下文里写代码。

Q22: 如果让你从零搭建一个 AI 应用的开发环境，你会怎么做？
A: 三步：
1. 项目上下文：写 CLAUDE.md（架构、偏好、常用命令）
2. 流程固化：写 SKILL.md（构建/部署/发版的标准流程）
3. 记忆管理：把设计决策写进 memory 文件
目标是：换一个 AI 工具、换一台电脑，看一遍这些文件就能继续开发。

Q23: AI 应用怎么做错误处理？
A: AI 应用的特殊性：错误源不是只有代码 bug，还有 LLM 本身的不确定性。
三层错误处理：
1. LLM 层：超时兜底、格式 fallback、空响应处理
2. 网络层：重试机制、降级策略
3. 业务层：看门狗、状态恢复、用户友好提示
核心原则：永远不要让用户看到"系统错误"——任何情况都要优雅降级。

Q24: 你怎么跟上 AI 领域的变化速度？
A: 不是追每一个新模型/新框架。策略是：
- 用最稳定的（DeepSeek → 作为主力 API）
- 关注最有潜力的（Claude → 备用 Provider）
- 保持架构灵活（多 Provider 适配，模型名可通过配置文件切换）
真正重要的是理解底层不变的东西——Prompt 设计原则、Agent 架构模式、Token 管理
——这些不会因为模型换代而过时。

Q25: AI 时代程序员的核心竞争力是什么？
A: 三个在上升的能力：
1. 系统设计：AI 能写代码但不会设计架构
2. 调试和判断：AI 写的 bug 更隐蔽，需要更强的排查能力
3. 需求翻译：把模糊的需求变成 AI 能执行的精确指令
一个在下降：从零手写代码的速度不再重要。
终极能力：知道"该让 AI 做什么"和"该自己做什么"的边界。

五、项目实战深挖（5 题）
===========================================================

Q26: 介绍一个你做过的最复杂的 AI 项目。
A: 桌宠 mibo——Tauri + TypeScript + Rust，多 Provider LLM 集成。
核心挑战：13 种状态 + 3 层锁 + 看门狗 + 多事件源（剪贴板轮询/窗口检测/用户交互
/定时器）并发管理。
最得意的设计：睡眠系统的 14 个拦截点全覆盖 + 3 种唤醒路径互相兜底——这个设计
本身就是 Agent 可靠性工程的体现。

Q27: 这个项目里你踩过什么坑？怎么解决的？
A: 三个典型案例：
1. CELEBRATE→HAPPY 被 5s 冷却阻断 → 把 CELEBRATE 加入冷却豁免
2. 零点 AI 回答锁挡住睡眠切换 → SLEEP 加入所有锁的白名单
3. 熄屏唤醒误触发 SLEEP → 加 idle ≥ 2h 判定为唤醒，重置计时
共同模式：都是"特定时序下的状态冲突"——状态机调试的核心难点。

Q28: 为什么用 Tauri 而不是 Electron？为什么是 macOS 专属？
A: Tauri 体积 10MB vs Electron 200MB，Rust FFI 直接调 macOS 原生 API。
macOS 专属是因为用了 NSWorkspace、CGWindowList、AppleScript——这些都没有
Windows 对应。跨平台需要为每个系统写不同的检测逻辑，目前先聚焦 macOS。

Q29: 如果让你给这个项目加一个"智能体"特性，你会加什么？
A: 主动学习提醒闭环：检测到编辑器 + 番茄钟结束 → LLM 总结"你刚才学了什么"
→ 用户一句话确认 → 自动记录到学习日志。
技术点：涉及 Function Calling（调用笔记 API）、多轮对话、上下文摘要。
目前没做是因为番茄钟只计时不分析——但架构上只需加一个"总结"的 API 调用。

Q30: 你从这个项目中学到最重要的一件事是什么？
A: "AI Agent 的难点不在 AI，在可靠性。"
LLM 回答质量波动可以接受，但状态机死锁、按钮消失、定时器漂移——这些才是用户
卸载的原因。Agent 产品的核心竞争力不是"模型有多强"，而是"系统有多稳"。
所以我把最多的时间花在锁系统、看门狗、交叉守卫上——这些才是 Agent 工程的核心。
